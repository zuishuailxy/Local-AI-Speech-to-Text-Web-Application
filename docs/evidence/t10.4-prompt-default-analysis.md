# 中文领域 prompt 默认启用的影响评估

- 日期：2026-10-28
- 分支：`main`
- 模型：faster-whisper 1.2.1 / Whisper small / CPU int8 / beam 5 / VAD
- 结论先行：**不建议默认启用**；已提供显式 opt-in `ASR_INITIAL_PROMPT`，默认空，行为不变。

## 默认启用会改变什么

启用后，每个中文请求都会把 prompt 作为 `initial_prompt` 传给 Whisper：

- 批量上传：`POST /api/transcribe`（language=zh）
- 实时识别：`/ws/transcribe` 的每个 partial（3 s 窗口）都会带 prompt
- 英文请求、auto 请求不受 prompt 影响（当前实现按语言/时长门控）

Whisper 的 `initial_prompt` 不是“热词表”，而是**解码条件**：它会改变模型对整段音频的语言、用词和断句先验。收益和风险都来自这一点。

## 实测收益

`samples/chinese.wav`（12 s，CER 参考 `samples/reference.txt`）：

| 配置 | CER | 推理耗时 | 输出 |
| --- | ---: | ---: | --- |
| 无 prompt | 0.2308 | 3.05 s | 轻轻地我走了,占如我轻轻地来。我轻轻地抓手,做别西天的云彩。那河畔的金牛是西洋中的新娘。 |
| 领域 prompt | 0.2051 | 3.26–4.38 s | 轻轻地我走了,占如我轻轻地来。我轻轻地抓手,作别西天的云彩。那河畔的金牛,是西洋中的新娘。 |
| hotwords（对照） | 0.2051 | 2.80 s | 断句变差，字面相近 |

收益只有 1 个字符（“做别”→“作别”），CER 从 0.2308 降到 0.2051（约 2.6 个百分点）。占如、抓手、金牛、西洋等近音错误全部保留——**prompt 无法弥补 small 模型的声学误差**。

## 默认启用的弊端（实测）

### 1. 短音频会把 prompt 词“读”进结果

1.0 s 英文音频 + 中文 prompt（language=en）：

```text
无 prompt:  Thank you.
有 prompt:  别测试：识别。      ← 输出语言被 prompt 带偏
```

这是最严重的一类：prompt 内容泄漏成识别结果，用户会看到完全无关的中文。

### 2. 短中文/低信息音频会替换真实内容

2 s 中文片段：

```text
无 prompt:  真心的我走
有 prompt:  轻轻地握着。      ← 不是“修正”，是改写
```

同一片段用 hotwords 也出现 `轻轻地握着`，说明短窗口下的先验注入本身有风险，不只是 prompt 文案问题。

### 3. 英文短音频出现新增幻觉

3 s 英文 + 中文 prompt：

```text
无 prompt:  Never give up never
有 prompt:  Never give up. Never lose your mind.   ← 原文是 “Never lose hope”
```

5 s 英文也从 `Always.` 变成 `always have hope.`。长英文样本（9 s）WER 仍为 0，说明风险集中在短音频和实时 partial。

### 4. 延迟上升且不稳定

同一 12 s 音频重复测量：

```text
无 prompt:   3.05 s
有 prompt:   3.26 s / 3.76 s / 4.38 s
```

最高增加约 1.3 s（+43%）。prompt token 需要预填充，且会占用 Whisper 448 token 的解码上下文；prompt 越长，剩余空间越小。实时 partial 本来就只有 3 s 窗口、1.3–2.0 s 推理预算，默认加 prompt 会直接挤压延迟目标。

### 5. 收益不可泛化

- 只在一个 12 s 样本上验证，没有统计意义。
- prompt 对领域词有效，但会改变所有中文音频的先验；新闻、口语、电话音、噪声场景没有数据。
- 领域不匹配时，prompt 里的词可能被“听”出来，尤其在静音边缘、咳嗽、口头语附近。
- 目前没有逐请求 prompt，默认启用等于给所有用户绑定同一领域假设。

### 6. 可观测性和隐私

- prompt 是配置项；若运维把客户名、项目名、内部术语写进 `ASR_INITIAL_PROMPT`，配置文件和部署脚本就成了敏感信息载体。
- 本项目的日志只记录 `initial_prompt=on/off`，不记录 prompt 内容和识别文本；默认启用会让“为什么这段识别成这样”更难归因。

## 当前实现（opt-in）

```bash
ASR_INITIAL_PROMPT='以下是普通话语音识别测试，包含：语音识别、实时语音识别、本地语音识别。' \
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

门控规则：

- 默认空字符串 → 不传 `initial_prompt`，与优化前完全一致。
- 仅 `language=zh` 显式请求使用；`auto` 和 `en` 不使用。
- 仅音频 ≥ 3.0 s 使用；更短的片段（含实时 partial）不使用。
- 最长 500 字符，超长启动失败并指名 `ASR_INITIAL_PROMPT`。
- 日志只记录 `initial_prompt=on/off`，不记录 prompt 正文。

## 建议

1. **保持默认关闭**：当前收益不足以抵消短音频/实时场景的幻觉与语言带偏风险。
2. 需要领域词时，用 opt-in 在**批量、较长、单一领域**的音频上启用，并用真实样本复测 CER 和幻觉。
3. 实时识别不建议启用 prompt；partial 窗口短，最容易出现 `真心的我走 → 轻轻地握着` 这类改写。
4. 若目标是稳定提升中文准确率，优先级应是更大模型 / 更好的麦克风与静音处理 / 领域数据微调，而不是全局 prompt。
5. `hotwords`（faster-whisper 1.2.1 支持）在本次样本上 CER 相同、延迟略低，但短音频同样出现改写；如后续要做热词，需要独立评估，不应直接默认开启。
